# 分組演算法與評分

## 比較順序

人數上下限內，列舉所有可行組數，維持各組人數差最多一人。無可行組數時使用最接近的均衡方案，並顯示範圍無法滿足的警告。

每個組數先以稀缺角色建立初始解，再用模擬退火改善；整體搜尋預算分配給所有候選組數。搜尋先減少「最低角色門檻」缺漏，再改善角色、曲風及性別加權分數。60 人以內額外檢查所有兩人交換，直到無法再以單次交換降低角色缺漏。

跨組數比較先最小化每組平均角色缺漏，以免組數多寡本身扭曲比較；達成相同程度後，使用：

`(1 − 人數偏好權重) × 分組綜合分數 + 人數偏好權重 × 人數偏好分數`

偏好人多時，可行的最少組數為 100 分，最多組數為 0 分；偏好人少時相反，其餘線性內插。「都可以」忽略人數偏好分數。權重為 100% 仍不能取代最低角色門檻。畫面綜合分數是角色、曲風、多元平衡的評估，不含選組數的人數偏好。

## 配置評分

以角色與成員職責槽進行增廣路徑匹配。每位成員最多一項樂器與一項人聲職責，因此可以自彈自唱，但不能同時彈兩種樂器；主唱與和聲共用人聲槽。這是產品採用的分工假設，可在建議分工中確認。

優先匹配稀缺角色。每項目標角色最多貢獻一次分數，配置分數是「已分配角色稀缺權重 / 全部目標角色稀缺權重」。只有所有所選角色都有可行分工，才能獲得 100 分。舊 `keyRoles` 設定遷移為 `desiredRoles`，最低門檻也依此計算。缺漏扣分依每組平均缺漏計算，避免組數增加導致分數無意義地歸零。取消僅按多才社員人數扣分的懲罰，角色分工與缺漏已直接衡量可用能力。

## 曲風與結果說明

雜食偏好採中性相似度 0.5，且不能產生共同曲風或共識加分；單人成組同樣無法證實共同偏好。角色稀缺警告、每組分工與缺漏會顯示給房主。重新分組由伺服器產生新種子；傳入相同測試種子仍可重現。

## 驗證與限制

`tests/engine/host-preferences.test.ts` 使用使用者提供的 24 人能力清單重建測試資料，直接驗證名單完整性、實際角色分工、木箱鼓分散、缺漏不能滿分及偏好選組數。這些結果不是線上房間讀回。

搜尋是啟發式，不保證全域最佳解。大於 60 人略過完整交換修復以控制執行時間。本機效能測試不等同正式 Cloudflare CPU 時間或正式部署驗收。與隨機基準比較分數，不能獨立證明使用者滿意度。
